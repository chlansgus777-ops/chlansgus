F01 — 매수가·손익비 보호를 이전 판단 유지 로직이 덮어씀

위치: domain/decision.py:212, domain/what_changed.py:diff, domain/freshness.py:233.

재현: 손절 90, 목표 120이면 최소 손익비 2의 최대 매수가가 100입니다. 가격이 99.9에서 100.1로 움직이면 손익비는 약 2.03에서 1.97로 내려갑니다. ATR 2에서는 구간 이탈폭이 0.25 ATR보다 작아 diff()가 중요한 변화로 보지 않습니다. decide()는 먼저 WAIT를 계산한 뒤, 이전 BUY를 다시 최종 판단으로 복원합니다.

별도 반례에서는 같은 시각의 100.1 시세와 최대 매수가 100을 전달해도 recommendation_freshness()가 CURRENT/actionable=True를 반환합니다. 시세가 분석 시각보다 엄격히 나중일 때만 먼저 재검증하기 때문입니다. 따라서 UI 재검증이 이 결함을 항상 막아준다고 할 수도 없습니다.

수정 방향: 판단 흔들림 억제는 점수 등급에만 적용하고, 최종 BUY/BUY SMALL/ADD 직전에 현재 가격·손익비·손절·비중 조건을 다시 강제해야 합니다. 생성 직후의 계획도 유효성을 확인해야 합니다. 매수의견과 지금 실행 가능 여부를 별도 상태로 관리하는 것이 좋습니다.

F02 — 보유 중 HOLD로 바뀌면 손절 감시 중단

위치: application/pipeline.py:598–604, application/services.py:_previous_lookup.

재현: 보유 종목의 직전 분석이 HOLD, 손절 100이고 이후 완료된 일봉 종가가 95인 입력을 사용했습니다. 결과는 HOLD, 거부권 없음이었습니다. 손절 이탈 검사 자체가 직전 action이 BUY/BUY SMALL/ADD인 경우로 제한되어 있습니다.

이는 흔한 BUY → 실제 보유 → HOLD → 하락 흐름에서 나타날 수 있습니다. 또한 매번 현재가에서 새 계획을 만드는 구조이므로 진입 때의 손절을 최근 분석의 새 손절로 바꾸지 않도록 별도 관리해야 합니다.

수정 방향: 추천 스냅샷과 보유 포지션의 활성 계획을 분리합니다. 진입 시 손절·계획 ID·주식 기준을 저장하고 HOLD에서도 계속 검사해야 합니다. 손절 변경은 명시적인 규칙과 변경 기록을 거쳐야 합니다. 사용자가 외부에서 산 기존 보유분은 활성 계획 미설정 상태를 명확히 표시해야 합니다.

F03 — 장후 실적 시각 누수

위치: domain/earnings.py:pair_with_releases, application/pipeline.py:earnings_visible.

재현: 17:00 ET에 공개된 것으로 전달한 실적 입력을 16:01 ET 조회에서 이미 사용할 수 있었습니다. 원천 함수는 datetime을 받지만 EarningsReport에는 날짜만 남기고, 같은 날 정규장 마감부터 허용합니다.

이번 반례는 과거 시점 조회를 대상으로 하므로 P2입니다. SEC 접수 시각과 실제 보도자료 공개 시각도 항상 같은 것은 아닙니다. 현재의 날짜 변환만으로 “늦게 잡혀도 미래 정보가 새지 않는다”는 문서 주장을 충족하지 못합니다.

수정 방향: 검증된 published_at/accepted_at과 출처를 보존하고 분석 시각과 직접 비교합니다. 시각이 없으면 다음 세션부터 쓰는 등 보수적인 규칙을 명시합니다.

F04 — 혼합 단위 가이던스 1,000배 오류

위치: domain/guidance.py:_parse, 약 109행.

입력: Revenue for the third quarter of fiscal 2026 is expected to be $900 million to $1.1 billion.

기대 범위는 9억~11억 달러입니다. 실제는 9,000억~11억 달러, EXTRACTED, MEDIUM입니다. 오른쪽 billion을 왼쪽 900에도 적용했고, low > high도 차단하지 않습니다.

수정 방향: 각 끝점에 독립적으로 단위를 적용하고, 단위가 생략된 경우에만 명시된 단위를 공유합니다. low ≤ high, 통화 일치, 유한한 값 등 기본 불변조건에 실패하면 GUIDANCE_UNCLEAR로 보내야 합니다. GAAP/non-GAAP 및 수준/변화량 검증과 별개로 단위 검증이 필요합니다.

F05 — 일시적 목록 누락이 즉시 상장폐지가 됨

위치: application/market_store.py:sync_universe, 약 156행.

재현: ABC와 KEEP이 상장되어 있고 ABC의 다음 날 거래 일봉도 저장되어 있습니다. 다음 SEC 목록에서 ABC만 빠지면 즉시 delisted_at이 설정됩니다. _really_delisted()의 거래 지속 검사는 돌아온 종목을 처리할 때 실행될 뿐, 최초 누락 순간을 막지 않습니다.

영향: 정상 종목의 스캐너 제외와 가짜 상장폐지 성과가 발생할 수 있습니다. update_outcomes()는 이미 기록된 horizon을 다시 계산하지 않으므로 나중에 GAP으로 철회되어도 잘못 기록한 성과의 별도 정정 경로가 필요합니다. 이번 테스트는 잘못된 delisted_at 기록까지 직접 재현했으며, 성과 오염 경로는 연결 코드 검토로 확인했습니다.

수정 방향: 목록 누락은 우선 PENDING/UNRESOLVED로 두고, 거래 지속 여부와 독립된 종료 근거를 확인합니다. 불확실한 상태는 마지막 가격으로 성과를 확정하지 않습니다.

F06 — 티커 재사용 시 새 회사 가격까지 이전 회사에 귀속

위치: application/sync.py:run의 일봉→유니버스 순서, application/market_store.py:_archive_reused.

재현: 옛 ABC(CIK 111)의 100달러 일봉 뒤에 새 ABC(CIK 222)의 10달러 당일 일봉을 먼저 저장하고 유니버스를 동기화합니다. 현재 코드 순서 그대로입니다. 아카이브 시 날짜 조건 없이 모든 PriceBarRow를 이동하여 새 회사의 10달러 일봉이 ABC~111에 붙었습니다.

영향: 옛 회사가 90% 급락한 것처럼 보이는 이력이 만들어질 수 있습니다. 새 회사에서는 당일 가격이 빠집니다.

수정 방향: 공급자에서 받은 일봉을 임시 보관한 뒤 종목 동일성을 확정하여 저장하거나, security ID와 유효 기간으로 귀속을 나눠야 합니다. 실제 변경일을 모르면 추측해서 두 회사를 연결하지 않아야 합니다.

F07 — 앞부분이 없는 가격 이력을 완전한 응답처럼 반환

위치: application/data_access.py:bars, 약 114행.

재현: 9월 1~25일을 요청했지만 저장소에는 25일 하나만 있습니다. 공급자는 요청 구간을 반환할 수 있도록 구성했습니다. 현재 코드는 끝 날짜가 최근이라는 이유만으로 공급자를 호출하지 않고 하루만 반환했습니다.

이 문제는 신규 설치·부분 동기화와 과거 성과 조회에서 부족한 이력 회복을 막습니다. 스캐너의 60일 미만 제외는 일부 영향을 제한하지만, 데이터가 실제로 없는 것과 아직 안 받은 것을 구분하지 못합니다.

수정 방향: 시작·끝 범위와 예상 세션 수, 실제 누락 구간을 확인합니다. 종목별 무제한 호출 대신 작업 예산 내 보충 수집으로 연결하고, 완전성 상태를 반환합니다.

수정 방향: fiscal year·fiscal quarter·period_end와 통화·GAAP 기준을 표준화하고 일치할 때만 비교합니다. 텍스트 기간을 확정하지 못하면 수치 추출 자체가 가능해도 비교값은 비워야 합니다.

F10 — 티커 재사용 후 옛 회사 추천을 참조

F11 — 금리 동결을 금리 상승으로 해석

F12 — 주식분할 때문에 잘못된 손절 SELL

F14 — 읽기 GET이 분석을 실행하고 저장

위치: api/routes.py:stock, api/app.py:local_guard.

재현: 토큰을 설정하지 않은 서버에 Origin·클라이언트 헤더 없이 GET /api/stocks/NVDA?refresh=true와 cross-site/no-cors Fetch Metadata를 보냈더니 추천 레코드 1개가 생성됐습니다. 신규 종목의 일반 GET도 분석을 실행할 수 있습니다. 응답을 읽지 못하더라도 부작용 자체는 일어날 수 있습니다.

수정 방향: 분석·재분석은 보호된 POST로 이동하고 GET은 조회 전용으로 둡니다. 기본 서버에도 토큰을 적용하고, Fetch Metadata 검증과 호출 예산을 함께 사용합니다. 신규 분석이 필요한 조회는 명시적인 상태를 반환해야 합니다.

4. 의뢰 범위를 넘어선 제품 전체 보강 제안

아래는 위의 실패 반례와 구분되는 설계·운영 개선 제안입니다. 해당 항목마다 장애를 직접 재현했다는 뜻은 아닙니다.

4.1 “미국 전체시장 스캔”과 “전체 종목을 동일 깊이로 분석”을 구분

현재 설정은 stage2 400 → stage3 150 → stage4 60 → 최종 40, 선행 추정치 신규 조회는 상위 20입니다. 그 전에 기존 추정치 유무가 순위에 영향을 줍니다. 먼저 데이터를 받은 종목이 계속 선발되는 선택 편향을 점검해야 합니다.

권장 보강:

  • 유니버스 전체 수, 적격 수, 최신 일봉·재무·추정치 확보 수, 깊이 분석 수를 나란히 표시합니다.
  • 탈락 이유를 종목별로 검색 가능하게 만들고 “낮은 점수”와 “자료를 아직 못 받음”을 분리합니다.
  • 추정치 조회 예산 일부를 미조회 종목 순환에 배정하고, 핵심 후보 밖에서 누락된 좋은 종목이 얼마나 있는지 표본 검사합니다.
  • 기존 제한을 풀어 후보 3개를 억지로 만들지 않습니다. 유효 매수 후보가 없으면 관찰 후보와 다음 확인 조건을 제시합니다.
  • 클래스주 표기 및 동일 CIK의 여러 클래스는 종목 식별 설계에서 먼저 해결해야 합니다. 단순 문자열 치환만으로 충분하지 않습니다.

4.2 현재가 세션 표시는 있어도 장외시간 의사결정 능력은 별개

README는 실시간 호가·장외시간 시세를 제공하지 않는다고 명시합니다. 따라서 PRE/REGULAR/AFTER라는 표시는 현재 시세가 그 세션의 체결 가능 가격이라는 증거가 아닙니다.

권장 보강: 분석 기준 세션, 시세 발생 세션, 시세 시각, 지연 여부, 실행 가능한 판단 범위를 한 카드에서 보여 줍니다. 검증된 장외 시세가 없으면 정규장 종가 기반 관찰로 제한합니다. 프리·정규·애프터 각각에서 표본 종목으로 신선도·스프레드·시세 공백을 측정하기 전에는 “지금 사도 됨”을 확장하지 않는 것이 좋습니다.

4.3 사용자에게 필요한 매수 계획은 가격 외에 금액·비중·수량도 포함

현재 UI의 “정상 비중 / 절반 비중 / 소량”만으로는 사용자가 얼마를 살지 결정하기 어렵습니다. 실전 포트폴리오 기본 full_position은 5%인데 paper는 기본 10만 달러 계좌에 1만 달러를 배정하는 등 두 경로의 sizing도 다릅니다.

권장 보강: 총자산·가용현금·현재 보유·최대 허용 손실을 기반으로 추가 매수 최대 금액, 추가 주식 수, 매수 후 종목/업종 비중, 손절 시 예상 손실액을 계산합니다. F08 수정 후 하나의 계산 결과를 UI·AI·paper가 공유해야 합니다. 이 수치가 없으면 “내 포트폴리오에 적합”을 강하게 표현하지 않아야 합니다.

4.4 스윙 판단과 단타 판단의 제품 범위 확정

현재 핵심 가격 이력과 모의투자는 일봉이고, 추천 이후 첫 시가 진입이며, 20/60거래일 성과와 2~6주 영향 등을 사용합니다. 따라서 현재 구현은 스윙 중심 판단 보조에 더 가깝습니다. 실시간 단타·체결 최적화·옵션 감마를 계산한 시스템으로 설명하면 안 됩니다.

권장 보강: 메인 화면에서 보유 기간, 분석 주기, 유효 세션과 데이터 범위를 먼저 명시합니다. 단타까지 지원하려면 호가·장중봉·실행비용·세션별 리스크 검증이 별도 필요하며, 이번 안전성 결함 해결보다 먼저 기능을 확장할 이유는 없습니다.

4.5 뉴스 영향은 검증된 인과 모델이 아니라 규칙 기반 추정

뉴스 제목·요약의 키워드와 제한된 관계 그래프가 중심입니다. exposure_graph.toml의 관계·가중치에는 일반적인 출처 설명은 있지만 각 관계마다 공시 URL·기준일·매출 의존도 근거가 붙어 있지는 않습니다. 이것을 모든 이슈와 근미래 영향을 계산했다고 표현할 수 없습니다.

권장 보강: 사건 사실과 예상 영향을 분리하고, 영향 경로별 원문·작성 시점·근거 수준을 표시합니다. 기사 정정·철회·수치 변경·서로 모순된 독립 보도를 처리할 테스트가 필요합니다. 규칙이 분류하지 못한 중요 기사를 누락률로 측정합니다. F11처럼 중립을 방향성으로 바꾸는 로직을 우선 제거해야 합니다.

4.6 점수의 유효성과 데이터 정확성은 따로 검증

80점 이상이라는 기준, 항목 가중치, 기술적 목표가, 익스포저 강도는 구현되어 있다는 것만으로 수익 예측력이 증명되지 않습니다. 신뢰도도 성공 확률이 아니라 분류 여유·데이터 완전성에 가까운 수치입니다.

권장 보강: 운영 전 기간을 고정한 표본 외 평가, SPY·동일 업종·단순 규칙과 비교, 거래비용 민감도, 점수 구간별 성과, 국면별 안정성, 불확실성 구간을 보고합니다. 순위를 만드는 표본과 검증 표본을 분리하고, 장기 수익률 중첩과 같은 날 종목 간 상관을 고려해야 합니다. 최소 100개 표본 규칙과 사람 승인만으로 통계적 타당성이 확보되는 것은 아닙니다.

4.7 모의투자와 화면의 손절 전략을 일치시켜야 성과를 설명할 수 있음

화면은 종가 기준 손절, paper는 장중 손절이라는 차이가 문서와 화면에 명시되어 있습니다. 정직하게 밝힌 점은 장점입니다. 그러나 paper의 승률을 그대로 실제 표시 전략의 승률로 이해하면 다른 전략을 비교하게 됩니다.

권장 보강: 종가 판단→다음 시가 실행 모델과 장중 stop-order 모델을 별도 전략 ID로 나누거나, 사용자 선택 전략 하나와 일치시킵니다. 배당·합병 대가·거래정지·상장폐지 회수금의 지원 범위도 명시하고 가격수익률/총수익률을 구분합니다. 잘못된 원천 가격·종목 이력의 수정 후에는 성과를 버전으로 재계산할 수 있어야 합니다. 현재 재현(replay)은 저장된 입력의 재계산이지 저장 입력이 진실이었다는 검증은 아닙니다.

4.8 초보자용 UI에서 “왜 지금 이 행동인가”를 더 명확히

한국어 안내, 쉽게 보기, 용어 설명, 결측 구분과 상태 폴링은 장점입니다. 다만 Settings는 읽기 전용이고 .env, TOML 직접 편집을 요구합니다. 데이터 준비 화면에도 개발자용 공급자명·상태 코드가 많이 남아 있습니다.

권장 보강: 첫 실행에서 모의/실데이터 선택→필수 키 검사→남은 수집량→예상 대기→동기화 재개까지 연결합니다. 종목 페이지에는 지금 행동 / 최대 매수가 / 허용 금액 / 무효화 조건 / 다음 재확인 시각을 우선 배치합니다. “신뢰도 높음”에는 수익 확률이 아니라는 짧은 설명을 붙입니다. 화면 새로고침·일시 단절 시 이전 데이터의 날짜와 현재 상태를 계속 구분해야 합니다.

이번에는 실제 브라우저를 띄우지 못했으므로, 시각적 완성도·터치 영역·색 대비·모바일 넘침을 직접 평가했다고 주장하지 않습니다. 화면 관련 평가는 컴포넌트 코드와 51개 프런트 테스트에 기반합니다.

4.9 비용·속도·중단 복구를 사용자 단위로 검증

구조상 상위 5개 FULL, 다음 15개 LIGHT를 검토합니다. 문서상의 호출 수를 적용하면 재사용이 없는 스캔에서 최대 145회 수준의 LLM 호출이 생길 수 있습니다. 금액은 선택 모델·입출력 토큰·실제 재사용에 따라 달라지므로 이번에 비용을 산정하지 않았습니다.

권장 보강: 일일·스캔당 비용 상한, 실행 전 예상 범위, 취소, 종목별 중간 결과, 재개 체크포인트를 제공합니다. 실제 60종목 깊이 분석의 p50/p95 처리 시간, 부분 실패율, API 예산을 측정합니다. 단일 종목 분석과 전체 스캔이 겹칠 때 추정치 일일 예산·DB 쓰기가 안전한지도 부하 테스트해야 합니다. 현재 전체 스캔의 lock이 단일 종목 분석에는 동일하게 적용되지 않는 점은 추가 검증 대상입니다.

4.10 설치·백업·업데이트를 복구까지 시험

온라인 SQLite 백업과 integrity_check, 단일 인스턴스·부모 프로세스 감시, 로컬 Host/Origin 제한은 좋은 기반입니다. 반면 소스 ZIP만으로 Windows 설치 결과와 업그레이드 안전성을 보장할 수 없습니다.

권장 보강: 깨끗한 Windows에서 설치·키 설정·최초 수집·강제 종료·재시작·버전 업그레이드·백업 복원·제거 후 데이터 유지까지 자동 검사합니다. DB 스키마 변경 전 백업과 실패 시 복구 절차를 갖춰야 합니다. 운영 로그·진단 패키지를 내보낼 때 자격증명과 사용자 보유내역을 분리하고 최소화해야 합니다.

4.11 CI는 “동작했다”를 재현하는 환경까지 잠가야 함

프런트 job에서 빌드하더라도 backend job과 파일 시스템이 공유되지는 않습니다. 현재 backend E2E는 Playwright 또는 브라우저가 없으면 skip됩니다. Windows backend는 Linux lock 대신 의존성을 다시 해결하는 경로입니다.

권장 보강: 필수 E2E 전용 job에서 frontend build와 Chromium 설치를 수행하고, 그 job에서는 필수 테스트 skip을 실패로 다룹니다. 이번 반례를 CI에 직접 포함합니다. OS별 의존성 잠금과 실제 설치 파일 해시를 기록하고, 테스트 통과 수·skip 이유를 평가서에 자동 반영합니다.

4.12 실데이터 검증은 응답 성공을 넘어 정답 대조로 확대

문서의 마지막 13/13 검증은 4f3a663 시점 기록입니다. 평가 대상 2240992와 동일한 실행인지, 수정 이후 동작이 모두 유지되는지는 원본 로그와 SHA로 확인해야 합니다. live-verify의 숫자 존재·유한성·날짜 확인은 유용하지만, 잘못된 9,000억 가이던스도 유한한 수라는 점을 생각해야 합니다.

권장 보강: API 응답 성공과 계산 정확성을 별도 상태로 나눕니다. 다양한 회계연도·정정 공시·은행·적자기업·클래스주·분할·티커 변경 사례를 포함한 검증 세트를 고정하고, 수치마다 공식 원문과 자동/수동 대조 결과를 남깁니다. 무료 데이터 제약을 감추지 않는 대신 실제 지원 종목과 미지원 이유를 선명하게 제시해야 합니다.

6. 반례 실행 및 전달물

ZIP의 evaluations/eval7을 대상 저장소의 evaluations/eval7로 복사한 뒤 실행합니다. 기존 제품 코드는 수정하지 않습니다.

python -m pytest -q -o addopts="" evaluations/eval7

별도 폴더에서 실행할 경우에는 저장소 절대 경로를 지정할 수 있습니다.

MARKETLENS_SOURCE_ROOT=/absolute/path/to/marketlens python -m pytest -q -o addopts="" evaluations/eval7

Windows PowerShell에서는 $env:MARKETLENS_SOURCE_ROOT = 'C:\path\to\marketlens'로 지정한 뒤 pytest를 실행합니다. 테스트는 기존 backend/tests/helpers.py와 MOCK 서비스 fixture를 일부 재사용하므로 전체 대상 저장소가 필요합니다. 실제 공급자 호출이나 주문 실행은 하지 않습니다.

2240992에서의 기대 실행 결과는 15 failed입니다. 이는 결함이 재현됐다는 의미입니다. 수정 후에는 테스트의 요구 조건을 완화하지 않고 통과시켜야 합니다. 기간·단위·종목 ID 같은 스키마를 바꾸는 경우 입력 생성 부분은 새 계약에 맞게 이동하되 검증 의미를 보존해야 합니다.

첨부에는 전체 반례 출력, 백엔드 최종 실행 결과, 이전 반례 실행 결과, 테스트 대응표를 포함했습니다. 원본 ZIP과 소스는 수정하지 않았으며 이번 작업은 평가와 개선 방향 제시까지입니다.
