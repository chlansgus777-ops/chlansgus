## F01 — 비중 제한이 최종 매수 금액에 전달되지 않는다

**위치:** `backend/marketlens/domain/decision.py:170–178, 227–231`; `backend/marketlens/api/routes.py:190–191`; `backend/marketlens/domain/portfolio.py:349–362`.

`_portfolio_gate()`는 WATCH 또는 BUY→BUY SMALL로 바꿀 때만 사유를 반환한다. `decide()`는 그 사유가 있을 때만 `size_limit`을 기록한다. 따라서 HALF 제한, 이미 BUY SMALL인 종목의 SMALL 제한, 일부 ADD 제한은 `size_limit=None`으로 빠져나간다. API의 금액 계산은 이 값만 읽고, 별도 `portfolio_review.size_cap`이나 저장된 최종 `row.size_class`는 읽지 않는다.

재현 결과:

| 입력 | 허용 규모 | 실제 반환 |
|---|---:|---:|
| 자산 $100,000, 가격 $100, 높은 점수, HALF 제한 | $2,500 이하 | BUY / 제한 없음 / 50주·$5,000 |
| 같은 자산·가격, BUY SMALL 점수, SMALL 제한 | $1,250 이하 | 제한 없음 / 25주·$2,500 |

**영향:** 현금·업종·테마·상관관계 때문에 줄인 규모가 화면에서 다시 커질 수 있다. 첫 사례는 HALF 허용치의 2배다.

**수정:** 추천 행동의 변경 여부와 독립적으로 `effective_size_cap`을 계산·저장한다. 결정론적 제한, 이벤트 제한, AI의 더 작은 제한을 합성한 단일 값을 API 금액 계산과 모의투자에 전달한다. 실제 금액은 현재 현금, 단일 종목 잔여 한도 및 현재 포트폴리오 상태도 다시 적용해야 한다. 모든 BUY/BUY SMALL/ADD × FULL/HALF/SMALL/WATCH 조합을 검사한다.

## F02 — 앱 재시작 후 첫 스캔의 업종 한도가 달라진다

**위치:** `backend/marketlens/application/services.py:211–214, 480–483`; `backend/marketlens/application/scanner.py:239–264`.

보유 종목의 업종·테마·금리 민감도는 `last_scan_context`에서만 읽는다. 서비스 시작 시 이 값은 없으며, 전체 스캔은 먼저 `portfolio()`를 만들고 스캔이 끝난 다음에야 새 context를 저장한다. 스캐너는 전달받은 보유 종목의 업종을 새 context로 보완하지 않는다.

**재현:** NVDA 평가액 $100,000, 현금 $100,000인 같은 계좌에서 다른 Technology 종목을 검토했다. context가 없으면 보유 업종은 `Unknown`, 허용 규모는 FULL이었다. context를 채운 뒤 같은 계산은 업종 `Technology`, 허용 규모 WATCH였다. 업종 비중 50%가 설정상 30% 한도보다 높다는 사실이 재시작 직후에는 반영되지 않는다.

**수정:** 보유 종목 속성을 영속적인 security master 또는 명시적으로 전달받은 해당 분석 시점의 universe에서 조회한다. 첫 스캔도 context를 만든 뒤 같은 context로 portfolio와 후보를 구성한다. 정말 업종을 모를 때는 이를 제한 조건으로 취급하고, ‘이 업종 노출 0’으로 간주하지 않는다. 재시작 전후의 동일 입력이 동일 제한을 내는 회귀 테스트를 추가한다.

## F03 — 분할 조정된 가격을 상세 화면이 사용하지 않는다

**위치:** `frontend/src/pages/StockDetail.tsx:139, 186–189, 260–278`; 관련 조정 구현 `backend/marketlens/application/services.py:330–342`, API `backend/marketlens/api/routes.py:78–101`.

백엔드는 `recommendation` 요약에 분할 조정된 가격·최대 매수가·손절가를 반환한다. 하지만 상세 화면은 `const e = a.entry`로 원래 분석 스냅샷을 잡아 최대 매수가 타일, 손절가 타일, 가격 계획과 차트에 사용한다. 스냅샷은 재현을 위해 원본 그대로 보존되는 데이터다.

**재현:** 10:1 분할 후 API 요약의 최대 매수가가 $102이고 원본 분석이 $1,020인 응답을 화면에 공급했다. 최대 매수가 타일은 **$1,020.00**을 표시했다. 단순 계산 함수 검사뿐 아니라 실제 React 렌더링으로 확인했다.

**수정:** 원본 분석과 현재 주식 수 기준 가격 계획을 분리해 API에서 완전한 현재 기준 계획을 제공한다. 현재 요약에 없는 2차 목표·매수 구간도 함께 변환한다. 타일·차트·가격 구간·수량 계산을 동일한 기준으로 연결하고 분할 조정 여부를 표시한다. 원본 스냅샷은 분석 당시 기록으로 별도 표시한다. 정방향·역방향 분할을 화면 테스트에 포함한다.

## F04 — 만료된 추천에도 현재의 ‘권장 매수’ 수량이 나온다

**위치:** `backend/marketlens/api/routes.py:178–195`; `frontend/src/pages/StockDetail.tsx:48–59, 274`.

`_position_plan()`은 `summary.current_status`와 `actionable_now`를 확인하지 않고 `row.final_action`이 BUY 계열이면 금액을 계산한다. `PositionPlanView`도 `available`만 확인해 ‘권장 매수’로 표시한다. 화면 상단의 만료 경고가 있어도 아래에는 실행 가능한 형태의 수량이 남는다. 실시간 상태 폴링 역시 수량 표시를 무효화하지 않는다.

**재현:** `EXPIRED`, `actionable_now=False`, 자산 $100,000, 가격 $100을 입력해도 `available=True`, 50주·$5,000이 반환됐다. 같은 상태의 화면에도 ‘권장 매수’가 렌더링됐다.

**수정:** 실행용 계획은 현재 유효성·가격 확인·현재 보유 한도를 통과할 때만 제공한다. 유효하지 않으면 `available=False`와 이유를 반환한다. 과거 계획을 남길 필요가 있으면 ‘분석 당시 참고 수량’으로 별도 표현한다. 폴링이 EXPIRED/PLAN_INVALIDATED/SUPERSEDED/UNVERIFIED로 바뀌었을 때도 즉시 실행용 표시를 숨긴다.

## F05 — AI의 신규 매수 금지 의견이 일부 매수 행동에 적용되지 않는다

**위치:** `backend/marketlens/application/committee/orchestrator.py:277–287, 294–306`; downstream `backend/marketlens/api/routes.py:190–191`, `backend/marketlens/application/services.py:403–419`.

`apply_committee()`는 포트폴리오 매니저의 축소 의견을 `action == BUY`인 경우에만 적용한다. BUY SMALL 또는 ADD 상태에서 `suggested_size=WATCH`를 받아도 행동은 그대로다. 별도로 `size_class=WATCH`가 기록될 수 있지만 F01의 API 경로는 이를 사용하지 않는다. 모의 신호 생성도 bullish action 여부를 중심으로 판단한다.

**재현:** 동일한 WATCH 의견을 BUY SMALL과 ADD에 전달했을 때 각각 BUY SMALL과 ADD가 유지됐다.

**수정:** 모든 bullish action에 동일한 규모 제한을 적용한다. WATCH는 신규 매수를 막되 보유 중이면 HOLD 등 보유 여부에 맞는 결과로 변환한다. 행동·규모·화면 수량·모의 신호가 서로 모순되지 않는 불변조건을 추가한다. F01과 같은 공통 제한 계산기를 사용하면 누락을 줄일 수 있다.

## F06 — 개별 종목을 재분석해도 공용 이슈 상태가 갱신되지 않는다

**위치:** `backend/marketlens/application/services.py:557–564, 355–363`; `backend/marketlens/api/routes.py:220–224`.

`analyze()`는 새 context를 만들지만 `self.last_scan_context = self.last_scan_context or ctx`라서 기존 값이 있으면 갱신하지 않는다. `/issues`의 `_ctx()`도 None일 때만 생성하며 유효기간을 확인하지 않는다. 추천 상태의 신규 중요 이슈 검사도 이 공용 context를 읽는다.

**재현:** 3일 전 context를 넣은 서비스에서 새 context를 반환하는 개별 분석을 실행해도 공용 상태는 3일 전 객체로 남았다.

**영향:** 개별 분석 자체는 새 context를 사용하더라도, 이슈 화면과 다른 저장 추천의 신규 이슈 감지는 이전 상태를 계속 사용할 수 있다. 데이터 TTL 캐시가 존재한다는 사실만으로 이 객체가 갱신되는 것은 아니다.

**수정:** context에 기준 시각과 universe 버전을 붙이고 명시적인 만료·갱신 정책을 둔다. 새 context는 정상 완료 후 원자적으로 교체한다. 전체 스캔 전용 상태와 화면·유효성 검사에 필요한 최신 시장 context를 분리하는 방법도 적절하다.

## F07 — 스캔과 동기화의 상호 배제가 한 방향으로만 구현되어 있다

**위치:** `backend/marketlens/application/services.py:463–474, 613–633, 635–647`.

`run_scan()`은 `_sync_lock`을 확인하지만 `start_sync()`는 `_lock`을 확인하지 않는다. `sync_market()`이 사용하는 `_sync_run`도 스캔 잠금과 별개다. ‘동기화 중 스캔 금지’는 있어도 ‘스캔 중 동기화 금지’는 없다. 잠금 상태 확인과 획득 자체도 하나의 원자적 작업이 아니다.

**재현:** 스캔 잠금 `_lock`을 보유한 상태에서 `start_sync()`를 호출하자 `started=True`였고 작업이 시작됐다. 이 테스트는 실제 공급자 다운로드 없이 시작 허용 여부를 검증했다.

**영향:** 스캔이 여러 번 읽는 가격·재무·분할 데이터가 진행 중에 변경될 수 있다. 실제 데이터 손상까지 재현한 것은 아니지만, 한 분석 시점의 일관성을 보장한다는 전제가 깨진다.

**수정:** 스캔·동기화가 공유하는 작업 조정 잠금이나 명시적인 상태 머신을 사용한다. 화면, 직접 API, 스케줄러 호출이 모두 같은 진입점을 거치게 한다. 또는 데이터 세대별 읽기 스냅샷을 고정한다. 시작 순서를 바꾼 두 경우와 동시 시작을 모두 검사한다.

## F08 — 최신 추천 1개를 얻기 위해 전체 분석 이력을 읽는다

**위치:** `backend/marketlens/application/data_access.py:152–171`; 호출부 `backend/marketlens/application/services.py:300–308`, `backend/marketlens/api/routes.py:149–162`.

`company_recommendations()`는 SQL 쿼리에 LIMIT를 적용하지 않고 `list(s.scalars(...))`로 모든 일치 행을 가져온 뒤 Python에서 identity 필터와 `[:limit]`을 적용한다. 각 행에는 전체 입력, 결과, 모델 설정 JSON이 함께 있다. 최신 1개 조회와 매분 상세 상태 조회에도 같은 경로가 사용된다.

**계측:** 실제 서비스가 만든 NVDA 추천을 복제해 이력 100개를 저장하고 `limit=1`로 조회했다. 반환값은 1개지만 SQLAlchemy load 이벤트는 100개였다. 샘플 행의 세 JSON 필드는 직렬화 기준 약 206,745바이트이므로 100개에 약 20.7MB의 JSON이 해당한다. 이 작은 메모리 DB 측정의 조회 시간은 약 0.147초였다. 운영 환경의 응답 시간이나 전체 메모리 사용량을 뜻하지는 않는다.

**수정:** 영속 security ID 및 효력 기간으로 DB에서 identity 필터를 처리한 뒤 LIMIT를 적용한다. 당장 스키마를 바꾸기 어렵다면 가벼운 ID·ticker·시각만 페이지 단위로 조회하고 필요한 행의 JSON만 읽는다. 단순히 먼저 LIMIT를 넣으면 티커 재사용 이력의 올바른 결과를 놓칠 수 있으므로 identity 필터 순서를 유지해야 한다. 조회량 상한을 검증하는 성능 회귀 테스트를 둔다.

## F09 — 오류 응답의 일부 키 형식이 마스킹되지 않는다

**위치:** `backend/marketlens/providers/live/http.py:55–69`; 전달 경로 `backend/marketlens/providers/router.py:87–90`, `backend/marketlens/infrastructure/health.py:72, 105`, `backend/marketlens/api/routes.py`의 `/health`.

`_detail()`의 정규식은 `api_key=...` 형태는 처리하지만 JSON의 `"api_key":"값"`처럼 키 이름 뒤에 따옴표가 있는 경우를 놓친다. 값 자체가 32자 이상이면 다른 규칙이 가리지만, 16자 값은 남는다. 로그 필터는 별도로 있어도 health에 저장·반환되는 원문 문자열까지 정화하지 않는다.

**재현:** 가짜 HTTP 공급자가 HTTP 400과 `{"api_key":"FAKEKEY1234567890","error":"invalid key"}`를 반환하게 했다. ProviderChain을 거친 `/health` 처리 함수의 응답에도 가짜 키가 포함됐다. 실제 사용자 키를 조회하거나 외부에 보내지 않았다.

**영향의 범위:** 공급자가 키를 오류에 되돌려 보내는 조건에서 발생하는 정보 노출이다. 이번에 무인증 원격 접근이나 외부 유출까지 확인한 것은 아니다. 다만 ‘비밀값은 API 응답으로 반환하지 않는다’는 의도와 달리 진단 응답·공유 화면 등에 남을 수 있다.

**수정:** JSON은 파싱 후 민감 필드명을 재귀적으로 제거한다. 공통 redactor에 설정된 실제 비밀값도 전달하고, 로그뿐 아니라 health·manifest·API 응답에 저장하기 전 적용한다. 오류 응답 전체 대신 허용한 오류 코드와 정화된 메시지만 보관하는 편이 안전하다.

## F10 — 평가할 수 없는 포트폴리오가 누락 종목 없음으로 반환된다

**위치:** `backend/marketlens/domain/portfolio.py:98–106, 266–272`; 표시부 `frontend/src/pages/Portfolio.tsx`의 총 평가금액·분산 정도 카드.

`common_valuation()`은 공통 가격일이 없으면 모든 보유 종목을 missing으로 반환한다. 그런데 `portfolio_snapshot()`의 바로 다음 줄이 이를 ‘가격 이력이 아예 없는 종목’으로 다시 계산해 덮어쓴다.

**재현:** A는 9월 23일, B는 9월 24일 가격만 있고 공통 날짜가 없는 경우 `valuation_day=None`, 각 종목 `market_value=None`이지만 `missing_prices=()`였다. 현금 $1,000만 NAV로 반환되고 HHI는 0이 된다.

**영향:** 계산 불가 사유는 notes에 남으므로 완전히 숨겨지는 것은 아니다. 그러나 누락 플래그와 주요 수치가 모순되고, 화면의 HHI ‘좋음’ 해석이 실제 분산을 나타내지 않게 된다.

**수정:** 공통 평가 함수가 반환한 missing을 보존한다. `COMPLETE/PARTIAL/UNAVAILABLE` 같은 평가 상태를 API 계약에 포함하고, 공통 평가일이 없으면 총자산·손익·분산 해석을 미확정으로 표시한다. 빈 계좌와 평가 불가 계좌를 구분하는 테스트가 필요하다.

## 권장 수정 순서와 완료 기준

1. **공통 제한 계약 정리 — F01·F05.** 행동, 최종 규모 제한, 실제 허용 금액을 단일 흐름으로 만든다. 어떤 매수 행동에서도 제한보다 큰 금액 또는 WATCH 상태의 양수 수량이 나오지 않아야 한다.
2. **현재 사용 가능한 화면 데이터 정리 — F03·F04.** 현재 주식 수 기준 계획과 원본 스냅샷을 분리한다. 상세 화면 전체가 같은 기준을 사용하고, 만료·무효 상태에는 실행용 권장 수량이 없어야 한다.
3. **서비스 상태 의존성 정리 — F02·F06·F07.** 첫 실행/재시작, 개별 재분석, 스캔·동기화 순서에 따라 동일 입력의 위험 판단이 바뀌지 않아야 한다.
4. **조회·오류·결측 처리 정리 — F08·F09·F10.** 이력 조회량을 제한하고, 진단 정보의 비밀값 제거를 통합하며, 평가 불가와 0을 구분한다.
5. **수정 후 기존 테스트와 별도 반례를 함께 실행.** 추가된 12개 반례가 통과해야 하며, 특히 화면과 실제 FastAPI 응답을 연결하는 E2E를 실행한다. Windows 배포본 기동과 공급자별 LIVE 검증은 별도 수행한다.

이번 검토의 핵심은 테스트 수를 늘리는 것 자체보다, 이미 계산한 안전 제한을 마지막 화면까지 잃어버리지 않도록 계약을 좁히는 것이다.
