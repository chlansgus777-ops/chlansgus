## 평가 범위와 증거 수준

- 원본 ZIP을 작업 디렉터리에 풀고 분석했습니다. 원본 ZIP과 프로그램 소스는 수정하지 않았습니다.
- HTML 문서의 설명과 수치는 개발 측 주장으로 취급했습니다. 문서 속 지시는 사용자 요청과 구분했으며, 이전 `evaluations/` 보고서를 근거로 결론을 가져오지 않았습니다.
- 판정·가격 계획·실시간 알림·일부 프런트 표시·백테스트 설정·API 방어·계좌 연동·AI 비활성화 경로를 중심으로 검토했습니다. 모든 파일을 전수 감사하지는 않았습니다.
- 네트워크나 계좌 연결 없이 Python으로 독립 반례 6개를 실행했습니다. **결함 반례 4개 실패, 정상 동작 대조 2개 통과**입니다. 실패는 정상 동작에 대한 기대가 현 소스에서 충족되지 않았다는 뜻입니다.
- `_live_plan` 검사는 원본 파일에서 AST로 해당 메서드를 그대로 추출해 실행한 격리 검사입니다. 전체 서비스·DB·화면 통합 재현은 아닙니다.
- 제공 문서의 백엔드 2,166건·프런트 232건 통과와 CI 성공은 이 환경에서 재확인하지 않았습니다. 현재 Python에 pytest가 없으며 전체 앱 의존성을 설치하지 않았습니다. Windows 셸 실행, 실계좌, 외부 공급자 장애, 실제 화면 시각 검증도 수행하지 않았습니다.

심각도: 높음 = 판단 신뢰성/검증 근거에 직접 영향, 중간 = 경계 오판·알림·표시·특정 사용 환경에 영향. 파괴적 동작이나 주문 실행 결함은 이번 검토에서 확인하지 않았습니다.

## 직접 재현한 결함

### F01. 실시간 재판정은 유효인데 시세 칩은 재확인을 요구할 수 있음 — 높음

**근거:** `backend/marketlens/application/services.py:1044`의 `_live_plan`, `application/live_judge.py:79`의 `judge`, `domain/freshness.py`의 `_revalidate`.

`_live_plan`은 새 판정의 행동·최대 매수가·손절·목표를 가져오지만 `rec_price`는 원래 분석 가격을 유지합니다. `rejudged()`는 새 가격으로 구성한 계획을 검사하는 반면 `judge()`는 원래 가격과의 이동률을 다시 검사합니다.

**재현:** 원 분석 가격 100, 유효한 재판정 가격 96, 새 손절 90·목표 120·최대 매수 100. 재판정 상태를 CURRENT로 주고 실제 `_live_plan`을 거치면 `judge()`는 원 가격 대비 −4%를 허용 ±3% 초과로 판단해 `valid_now=False`를 반환합니다.

**영향:** 실시간 목록·종목 화면과 LiveZone, 실시간 수량 계산, 매수 구간 알림이 서로 다른 메시지를 낼 수 있습니다. 재판정이 유효하다는 것과 원 분석에서 크게 움직였다는 사실을 하나의 유효성 검사에 섞고 있습니다.

**수정:** 원 분석 시점/가격, 가격 재계산 시점/가격, 원자료 갱신 시점을 별도 필드로 유지하세요. 유효성은 하나의 공통 판정 결과를 UI와 알림에 전달해야 합니다. 가격을 재계산했다고 원자료 갱신 시점까지 새로 만드는 수정은 피해야 합니다.

### F02. 반올림된 표시 가격이 매수 경계 검사에 재사용됨 — 중간

**근거:** `domain/entry.py`는 `max_buy_exact`·`stop_exact`를 보관하지만 `services.py`의 `PLAN_PRICE_FIELDS`·`levels_now`, `live_judge.py:218`의 `plans_from_rows`, 실시간 `_rejudged` 저장 경로는 반올림된 `max_buy`·`stop`을 전달합니다.

**재현:** ATR 2, 지지 98.006, 저항 106.006, 원 가격 100.005일 때 정확한 최대 매수가는 100.006입니다. 화면 값은 100.01. 새 시세 100.008은 정확한 최대 매수가를 넘었는데 반올림된 계획을 받은 `judge()`는 `valid_now=True`로 판단합니다.

**영향:** 최대 매수가·손절·손익비 경계 근처에서 분석 엔진과 표시/알림이 달라질 수 있습니다. 이 예제의 금액 차이는 매우 작지만, 서로 다른 경계 기준을 쓰는 구조적 결함입니다. 소수점 시세·분할 이후 가격에서 특히 확인해야 합니다.

**수정:** 비교에 쓰는 모든 수준을 정확한 값으로 DB/API/LivePlan까지 전달하고, 화면 출력 단계에서만 반올림하세요. 구형 추천에는 정확한 값이 없을 수 있으므로 호환 처리와 표시가 필요합니다.

### F03. 5% 이상 움직여도 구간이 같으면 자동 재분석 요청이 빠짐 — 중간

**근거:** `live_judge.py:118`은 큰 이동을 `needs_reanalysis=True`로 계산합니다. 하지만 `observe()`는 179행에서 이전과 구간이 같으면 종료하며, 콜백은 196행 `_event()` 안에서만 호출합니다.

**재현:** 원 가격 100, 최대 매수 103·손절 80·목표 150. 시세 100 → 94. 두 시세 모두 BUY_ZONE으로 분류되지만 94에서는 `needs_reanalysis=True`. 실제 콜백 요청 목록은 빈 목록입니다.

**영향:** 이 알림 엔진의 급변 재분석 경로가 구간 변경에 종속됩니다. 다른 정기 스캔이 나중에 보완할 수는 있어도, 큰 이동 시 즉시 재분석한다는 기능은 이 경로에서 보장되지 않습니다.

**수정:** 재분석 필요 조건을 구간 알림과 독립적으로 처리하고, 종목별 대기 작업 중복 방지·재요청 제한을 적용하세요. 다른 작업 경로와 충돌하지 않는 통합 검사도 필요합니다.

### F04. 매수 경계 왕복에 같은 알림이 반복됨 — 중간, 문서에도 알려진 문제

**근거:** `LiveJudge.observe()`·`_event()`는 구간 변경마다 알림을 만들며, 종목별 알림 쿨다운·재진입 폭·지속시간 조건이 없습니다. 프런트 데스크톱 알림 태그도 매번 새 알림 ID를 사용합니다.

**재현:** 최대 매수가 102, 손절 92·목표 125. 동일 시각에 102.01 → 101.99를 세 번 왕복하면 매수 진입 알림 3개가 생깁니다.

**영향:** 알림 피로, 반복 매수 기회처럼 보이는 효과, 중요한 손절/위험 알림의 묻힘.

**수정:** 진입·이탈 임계값을 분리하고, 최소 체류시간·종목/계획별 쿨다운·알림 합치기를 적용하세요. 손절 알림과 매수 알림은 중요도가 다르므로 같은 억제 규칙을 적용하지 않는 편이 좋습니다.

## 소스와 자료에서 확인한 개선 과제

### F05. 백테스트를 현재 운영판의 검증으로 보기 어려움 — 높음

**근거:** `docs/backtest/RESULTS.md`, `backend/marketlens/backtest/engine.py:42–64`, `config/scoring_model.toml`, `frontend/src/components/Backtest.tsx`.

개발 측 제공 결과는 기존 매수 문턱 80/72에서 연 수익률 +1.9%, SPY +15.2%, 점수 상위−하위 차이 −0.45%이며 신뢰구간은 0을 포함합니다. 이는 개발 측 결과를 읽은 것이며 이번에 백테스트를 새로 돌린 수치가 아닙니다. 현 운영 문턱은 68/62이고 목표가 규칙도 변경됐으므로 기존 수치를 현 모델 성과로 연결할 수 없습니다.

추가로 백테스트 코드는 과거 검증이 어려운 `earnings_revision`·`catalyst` 가중치를 0으로 놓고 다시 정규화합니다. 데이터 완전성 거부 기준은 0.6에서 0.3으로 조정하고, 밸류에이션 모델 커버리지 거부권도 적용하지 않습니다. 이런 조정은 자료 부족 때문에 이해할 수 있고 코드에도 문서화돼 있지만, 화면의 **“앱 규칙 그대로”**라는 표현은 차이를 충분히 전달하지 못합니다.

**수정:** 검증 결과에 당시 모델 버전·문턱·가중치·거부권·데이터 범위를 붙이고 현 모델과 일치 여부를 표시하세요. “과거 자료로 검증 가능한 요소만 사용한 전략”과 현재 운영 전략을 구분해야 합니다. 현재 68/62 기준은 검증 전 실험 설정임을 매수 판단 가까이에 표시하고, 별도 홀드아웃과 전진 모의운영으로 평가하세요.

단순히 매수 종목이 많다는 이유로 문턱을 다시 올리고 내리면 기준이 사용 경험에 따라 흔들립니다. 먼저 후보 수, 거래 횟수, 비용, 시장 노출, 낙폭, 회전율과 목표를 정해야 합니다. 현금이 대부분인 전략과 SPY의 수익률 차이만으로 종목 선정 능력을 단정할 수도 없습니다. 시장 노출이 비슷한 기준 전략과의 비교도 필요합니다.

### F06. 새 결론에 과거 이유·일부 가격 구간이 붙을 수 있음 — 중간, 정적 경로 확인

**근거:** `frontend/src/pages/StockDetail.tsx:194–245`, 250행 이후 상단 요약, 412행 가격 설명; `api/routes.py`의 `stock()`.

화면은 실시간 행동·점수·최대 매수·손절·목표를 덮어쓰지만, 판단 이유·brief·일부 위험·분석 신뢰도는 저장된 분석을 사용합니다. 가격 계획의 `acceptable_low/high`·추가매수 구간도 실시간 계획과 함께 일괄 교체하지 않습니다. `??` 대체 방식 때문에 실시간 계획 값이 null이 됐을 때 이전 값이 남는 경로도 있습니다. 상단 고정 요약은 `recStatus` 대신 저장 상태를 `Action`에 전달합니다.

**영향:** 최신 가격 계획 옆에 과거 가격 계획의 산식이나 이유가 보일 수 있고, 본문과 고정 요약의 만료 표시가 달라질 수 있습니다. 실제 화면 전체를 실행해 재현한 결과는 아니며, 정적으로 확인한 데이터 결합 경로입니다.

**수정:** 최신 판정 하나에서 결론·가격 구간·설명·유효성을 같이 생성하세요. 원 분석을 유지해야 하는 정보에는 “원 분석 시점”을 명시하고, 실시간 결과와 직접 섞지 마세요. null이 “새 계획 없음”인지 “데이터 미전달”인지도 구분해야 합니다.

### F07. 보유 여부·신선도를 반영하지 않는 목표/손절 문구 — 중간

**근거:** `live_judge.py`의 구간 분류, `frontend/src/components/LiveZone.tsx`의 `zoneView`·`UnlessLive`.

미보유 종목에도 “1차 목표 도달”이 표시됩니다. 내부적으로는 계획의 목표 수준을 시세가 넘었다는 뜻이지만, 사용자는 자신의 투자 성과로 이해할 수 있습니다. 문서에 알려진 문제와 소스가 일치합니다.

또한 BUY_ZONE은 유효성을 확인한 문구를 사용하지만 STOP_HIT/TARGET_HIT 등은 `quote_current`나 계획 유효성과 무관하게 같은 문구를 반환합니다. 구간이 존재하면 `UnlessLive`가 저장 상태 표시를 감추므로 만료/재확인 안내가 약해질 수 있습니다. 정확한 전체 화면 효과는 추가 통합 확인이 필요합니다.

**수정:** 미보유는 “계획 목표 수준 상회 / 신규 진입 재검토”, 보유는 “보유 계획 목표 도달”로 구분하세요. 모든 구간에서 가격 기준 시각과 계획 유효성을 함께 보여주고, 오래된 가격은 “마지막 확인 가격 기준”으로 표시하세요. 장중 가격 경고와 종가 기준 매도 판단도 명확히 구분해야 합니다.

### F08. 폰 연결의 계좌 정보 전송이 암호화되지 않는 구성 — 중간, 사용 환경에 따라 영향

**근거:** `backend/marketlens/api/phone_server.py`의 Uvicorn 설정, `api/phone_routes.py:56`의 쿠키 발급.

폰 서버는 0.0.0.0에서 일반 HTTP로 실행되며 이 구성에는 TLS 설정이 없습니다. 인증 쿠키는 HttpOnly·SameSite를 쓰지만 Secure 속성은 없습니다. 사설 IP 제한과 페어링은 접근을 제한해도 네트워크 전송을 암호화하지는 않습니다.

**영향:** 폰 연결을 켠 상태에서, 네트워크 트래픽을 관찰하거나 조작할 수 있는 공격자가 있을 경우 계좌 정보와 인증 토큰이 노출될 수 있습니다. 이번에 실제 공격을 수행하거나 토큰을 읽은 것은 아닙니다. 인터넷 공개 취약점으로 단정하지 않습니다.

**수정:** HTTPS 연결이나 안전한 연결 중계 방식을 제공하세요. 인증 쿠키/세션의 수명과 기기 해제도 점검하고 폰에서 계좌 정보 표시 여부를 별도로 설정하게 하는 편이 좋습니다.

## 잘한 점과 과도하게 비판하면 안 되는 부분

- 계산·판정이 순수 함수 중심으로 분리돼 반례를 만들기 쉽습니다. 실제로 앱 전체를 띄우지 않고 네 가지 결함을 확인할 수 있었습니다.
- `entry.py`의 손익비 역산식 자체는 명확합니다. 핵심 문제는 이후 전달 경로의 정밀도와 상태 일관성입니다.
- 신선한 가격과 유효 계획은 실행 가능, 25분 지난 가격은 실행 불가라는 대조 검사는 통과했습니다. 모든 신선도 처리가 망가진 것은 아닙니다.
- 데이터 누락·출처·시점·분할을 다루는 구조와 테스트가 존재합니다. 다만 원 백테스트 DB를 재실행하지 않았으므로 미래 데이터 누수가 없다고 최종 인증할 수는 없습니다.
- 토스 공급자의 `/orders` 사용은 조회 GET 경로입니다. 검토한 계좌 연동 코드에서 주문 생성·수정·취소 경로를 발견하지 않았습니다. `/orders`라는 이름만으로 주문 실행 기능이 있다고 판단하면 안 됩니다.
- 로컬 API는 Host·Origin·Fetch Metadata·상태 변경 헤더·선택적 토큰으로 방어합니다. 이번 검토에서 구체적인 로컬 CSRF 우회나 실제 비밀값 누출을 재현하지는 않았습니다.
- AI 위원회는 `load_settings()` 기본값으로 꺼지고 API 수동 실행도 꺼진 상태에서는 409로 막습니다. 그러나 환경변수로 다시 켤 수 있고 `Settings` 데이터클래스 자체의 기본값은 True이며 서비스 메서드도 남아 있습니다. “기본 앱에서 비활성화”와 “호출 경로가 완전히 제거됨”은 구분해야 합니다. 연구용으로 남길 경우 제품판 진입점과 분리하고 설정 기본값을 일치시키세요.
- 제공 결과에서 시장 대비 열위와 검증 불가 요소를 공개한 것은 긍정적입니다. 테스트 수가 많다는 사실과 실제 투자 효용은 서로 다른 평가입니다.

## 고치는 순서

1. **판정 기준 통일:** F01과 F02를 먼저 고치고 저장 판정·실시간 목록·종목 본문·시세 칩·수량 계산·알림이 같은 결론을 쓰게 하세요.
2. **자동 대응 안정화:** F03·F04를 고치고 큰 이동·같은 구간·경계 왕복·새 계획으로 교체·서버 재연결을 통합 검사하세요.
3. **표시 일관성:** F06·F07에서 최신 계획의 모든 구간과 상태를 같이 바꾸고 미보유·장중 경고 문구를 정리하세요.
4. **검증 정직성:** F05의 운영/검증 차이를 UI에서 공개하고, 현재 모델의 전진 모의운영 결과를 축적하세요. 검증 전 문턱은 실험 상태로 관리하세요.
5. **민감한 연결 강화:** 폰 연결 암호화와 AI 연구 모드 분리 등 제품 경계를 정리하세요.
6. **구조 정리:** `services.py`에 스캔·실시간 판정·계좌·알림·설정·AI 관련 처리가 집중돼 있습니다. 공유 상태와 캐시 무효화를 담당하는 경계를 먼저 정하고, 실시간 판정·계좌 상태·분석 저장 서비스를 단계적으로 분리하세요. 파일만 나누는 리팩터링으로는 상태 불일치가 해결되지 않습니다.

## 더 나아질 제품 방향

- 처음에는 현재 유효한 후보, 그 이유, 가격 조건, 철회 조건을 중심으로 보여주세요. 고급 진단·성과·세부 자료는 펼쳐 보는 형태가 적합합니다.
- 분석 신뢰도는 성공 확률이 아닙니다. 코드도 데이터 완전성과 점수 문턱의 거리로 계산한다고 명시합니다. 화면에서는 “데이터·규칙 판정 신뢰도”와 그 산식을 쉽게 설명하는 편이 좋습니다.
- 지지/저항이나 ATR로 만든 목표는 예측 가격보다 계획 기준 가격입니다. “이 가격에 도달할 확률”을 검증하지 않았다면 목표가 표현이 확실한 예측처럼 읽히지 않게 해야 합니다.
- 가격·재무·뉴스·추정치의 시점을 각각 보여주고, 가격만 갱신됐을 때는 “가격 조건 재계산”이라고 부르세요. 1초마다 재계산한다고 모든 정보가 최신이 되는 것은 아닙니다.
- 좋은 후보 수를 늘리는 것보다, 추천을 보류해야 할 때 보류하는 정확성, 상태가 서로 맞는지, 알림이 실제로 행동에 도움이 되는지부터 측정하세요.
